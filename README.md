# RL-дообучение последовательной рекомендательной модели на Yambda

В работе обучены последовательный рекомендатель по ID треков и модель вознаграждения, предсказывающая долю прослушивания. Затем рекомендатель дообучен методами REINFORCE и RLOO и сравнён с продолжением next-item-обучения. Отдельная серия посвящена дополнительным проходам Transformer по истории.

## Данные и оценка

Использован **Yambda-50M: 46,47 млн событий и 9 238 пользователей**. Это журнал прослушиваний, включая неполные, с признаками трека и долей прослушивания. Он позволяет оценивать прогноз следующего зарегистрированного действия и завершения прослушивания.

Разбиение общее для всех основных сравнений: последние сутки отведены под тест, предыдущие сутки — под validation; между частями оставлен 30-минутный интервал. История содержит строго более ранние события пользователя. События с одинаковым временем используют один предшествующий контекст. Каталог — **100 000 самых частых треков обучающей части**. Треки вне каталога сохраняются в истории как неизвестный токен.

Тест содержит **232 049 событий**; в журнале он назван R9. Целевые треки вне каталога — 34 520 событий — остаются промахами в знаменателе. Ранжирование проводится по всему каталогу без добавления правильного ответа в кандидаты. NDCG и Recall усредняются по событиям. Для одной целевой позиции Recall@100 — попадание в первые 100, NDCG@100 — `1/log₂(rank+1)` при попадании.

События делятся на органические и помеченные датасетом как рекомендованные. Во второй группе 117 291 событие. Отдельный результат по ней нужен, чтобы общий выигрыш не скрывал преимущественно прогноз повторных органических прослушиваний. Флаг описывает происхождение зарегистрированного события; полного журнала показов и отказов в данных нет.

Тест использовался повторно в ходе работы. Все приведённые тестовые сравнения имеют исследовательский статус. Для парных оценок использован 95%-й percentile bootstrap по пользователям: 1 000 выборок, с сохранением всех событий выбранного пользователя. Он оценивает неопределённость на этих данных при фиксированных обученных моделях.

## 1. Обучение исходного GPT-рекомендателя

Базовая архитектура — GPT-2-подобный каузальный Transformer: два блока, ширина 128, четыре attention-head, контекст 64 события. Входные и выходные item-эмбеддинги связаны; предсказывается следующий трек.

Для первой серии подготовлены 4,11 млн обучающих позиций: 10% от позиций с целевым треком в каталоге. При этом истории строятся из полного предшествующего потока событий. Модель seed 43 обучена за 16 058 обновлений с batch 256. В качестве простого контроля использована частота треков в недавней истории пользователя.

- GPT на этой подвыборке: **NDCG@100 = .0966**.
- Частотный метод по истории: **.1022**.

Так получена первая рабочая исходная модель для RL и обнаружен сильный простой baseline. Проверку большего объёма обучения описывает эксперимент 4.

## 2. Обучение и проверка модели вознаграждения

Модель вознаграждения (RM) получает историю и один трек, а предсказывает `min(played_ratio_pct/100, 1)`. Для истории используются средние 32-мерные эмбеддинги треков; для кандидата — его эмбеддинг, log-длительность и популярность на train. Полная RM — MLP 66→128→64→1 с GELU и sigmoid. Сравнивались варианты только с историей, только с треком и с обоими входами. Обучение: MSE, один проход по 4,11 млн позиций, batch 512, AdamW с lr .001.

Качество именно тех frozen RM, которые затем использовались в RL, проверено на 197 529 тестовых прослушиваниях с целями в каталоге:

| Предиктор доли прослушивания | Test MSE |
|---|---:|
| Среднее по train | .1847 |
| Только история | .1680 |
| История + трек + длительность + популярность | **.1631** |

Вариант с признаками трека улучшает прогноз. Для выбора рекомендаций важно следующее различие: history-only RM возвращает одну оценку для всех кандидатов одной истории. Она служит контролем прогноза по контексту пользователя и baseline для policy gradient. Изменять выбор трека могут только различия оценок между кандидатами. Поэтому общей ошибки RM недостаточно для оценки её пригодности как награды.

Во всех следующих основных RL-сравнениях полная RM заморожена. Она оценивает завершение уже наблюдавшихся прослушиваний; перенос её оценок на другие действия проверяется через поведение политики и релевантность.

## 3. Первое сравнение CE, REINFORCE и RLOO

Все варианты стартовали из одного GPT на 10% обучающих позиций. Каждому дообучению выделены 32 000 обновлений по 128 историй — 4,096 млн примеров; использованы seeds 17 и 29. Результаты CE и RL в таблицах — средние по этим двум обучениям.

Контроль CE продолжал предсказывать зарегистрированный следующий трек. В REINFORCE действие выбиралось из распределения модели, а преимущество считалось относительно замороженной history-only RM `b(h)`. В RLOO-8 для одной истории независимо сэмплировались восемь треков; baseline для каждого — средняя награда остальных семи. Это восемь альтернатив при одной реальной истории, а не восемь последовательных пользовательских действий.

Общая цель RL:

`J(π) = Eπ[RM(h,a)] − β KL(π || π₀),`

где `π₀` — замороженный исходный GPT. В основной серии β=.1; KL вычислялся точно по всему каталогу. При дообучении CE и RL dropout отключён, обновляются все параметры рекомендателя. Общие настройки: AdamW, lr `2e−5`, weight decay 0, gradient clipping 1. Сравниваются финальные checkpoints.

| Вариант от GPT на 10% позиций | Test NDCG@100 |
|---|---:|
| Исходный GPT | .0966 |
| Продолжение CE | **.1042** |
| REINFORCE, одно действие | .0958 |
| RLOO, восемь действий | .0960 |

- CE улучшила ранжирование; оба RL-варианта повысили RM-награду и остались ниже CE.
- Сравнение REINFORCE-1 с RLOO-8 меняло сразу число действий и baseline. Поэтому проведён дополнительный REINFORCE-8 с тем же замороженным `b(h)`.
- При одинаковых восьми действиях RLOO дала меньший разрыв по цели J до её точного одношагового оптимума: .00172 против .00227. Проверка отделяет эффект baseline от числа RM-оценок. Все эти числа относятся к первой исходной модели.

## 4. Повторение с GPT на полном обучающем пуле

Следующий GPT той же архитектуры обучен на всех **41,14 млн** доступных train-позиций: 160 714 обновлений с batch 256, AdamW lr .0002. Checkpoint seed 43 выбран по validation NDCG. Здесь одновременно выросли объём данных и число обновлений.

Из этого GPT снова запущены CE и RLOO-8. Их данные, порядок примеров, 32 000 обновлений, seeds и RM совпадают внутри сравнения. Это проверка сохранения результата при более сильном старте.

| Вариант от полного GPT | NDCG@100: весь тест | NDCG@100: рекомендованные события | Ожидаемая RM-награда |
|---|---:|---:|---:|
| Исходный GPT | .1213 | .0344 | .6595 |
| Продолжение CE | **.1262** | **.0371** | .6597 |
| RLOO-8, β=.1 | .1207 | .0343 | **.6641** |

Ранжирование рассчитано на полном тесте; ожидаемая RM-награда — на фиксированных 1 024 validation-историях с суммированием по вероятностям всех кандидатов.

- Сильный исходный GPT и продолжение CE дали более высокие результаты, чем первая серия.
- RLOO снова оптимизировала RM-награду. Преимущество CE по NDCG составило +.00545 с 95%-м пользовательским интервалом [+.00470, +.00613].
- На помеченных рекомендательными событиях RLOO близка к исходной модели; CE улучшает и этот срез.

## 5. Изменение β и точное reward-tilting

С полным GPT повторено RLOO-дообучение при β=.03 и .3. Остальная схема сохранена. Меньшее β ослабляет ограничение на отклонение от исходного распределения.

| β | Изменение ожидаемой RM-награды, п.п. | Изменение test NDCG@100 |
|---:|---:|---:|
| .03 | +1.62 | −.00649 |
| .10 | +.46 | −.00065 |
| .30 | +.16 | −.00009 |

Результат задаёт измеренный компромисс: сильнее оптимизируя RM, получаем больший выигрыш её score и большую потерю next-item-качества. При β=.3 интервал изменения NDCG включает ноль.

Для β=.1 дополнительно рассчитано точное распределение для этой одношаговой цели:

`q(a|h) ∝ π₀(a|h) exp(RM(h,a)/β).`

Для 100k-каталога его можно нормировать непосредственно. Этот контроль показывает, что даёт сама заданная цель при точной оптимизации, и позволяет измерять разрыв обученной политики до неё.

- На тех же 1 024 validation-историях NDCG точной q — .0885, исходного GPT — .0897; интервал разницы включает ноль.
- CE выше q на этой подвыборке; различие q и RLOO также статистически не установлено.
- Таким образом, у точного RM-оптимума здесь нет выявленного преимущества над исходным ранжированием. Эта подвыборка оставляет неопределённость в разделении ошибки оптимизации и несоответствия награды next-item-цели.

## 6. Проверки поведения и зависимости от истории

Для каждой из 10 000 validation-историй сэмплированы 16 действий из исходного полного GPT, CE и RL-политик.

- При β=.03 самый частый top-1 трек занимал около **2.7%** запросов против **.6%** у исходного GPT; при β=.3 доля осталась около .6%.
- Доля сэмплированных треков, уже встречавшихся в истории, изменилась с **13.4% до 13.8%** при RLOO β=.1.

Усиление RM-оптимизации сопровождалось концентрацией рекомендаций. Сдвиг к повторным трекам в основной β=.1 серии был небольшим. Полного анализа длительности и популярности сэмплированных действий нет, поэтому гипотеза предпочтения коротких треков остаётся открытой.

Чтобы проверить вклад пользовательской истории в RM, её заменяли историей другого пользователя, подобранного по длине и активности. Вход исходного GPT и признаки кандидатов оставались прежними. Точные q с настоящей и заменённой RM-историей сравнивались при одинаковом среднем KL.

- Распределения действий изменились.
- На четырёх уровнях KL интервалы различия NDCG включали ноль.

Эта проверка показывает чувствительность политики к RM-истории и отсутствие установленного выигрыша ранжирования от настоящей истории в данной диагностике.

## 7. Отдельная серия: дополнительные проходы Transformer

В этой ветви проверялось, помогает ли одному блоку несколько раз уточнять представление истории, и как это соотносится с обычной глубиной. Взята компактная адаптация [Huginn](https://arxiv.org/abs/2502.05171): входной блок кодирует историю, основной блок получает текущее состояние вместе с исходным представлением, выходной блок предсказывает трек. Основной блок применяется один или четыре раза; во втором случае его веса общие либо отдельные для каждой глубины.

Сравнены три варианта с историей 256 событий, одинаковыми train-позициями, 32,768 млн примеров на модель и seeds 17/29. Использованы RoPE, RMS-нормировка сумм residual, source-reinjection через конкатенацию и полный backward через все проходы. Loss находится только на конечном выходе:

| Вариант | NDCG@100 | Recall@100 | Параметры |
|---|---:|---:|---:|
| Один проход основного блока | .1468 | .2981 | 13.72 млн |
| Четыре прохода, общие веса | .1493 | .2990 | 13.72 млн |
| Четыре последовательных блока с разными весами | **.1580** | **.3062** | 14.51 млн |

- При том же числе параметров четыре shared-прохода улучшили NDCG относительно одного.
- Вариант с разными весами оказался сильнее в обоих seeds, при увеличении параметров на 5.75% и близком времени обучения.
- Четыре прохода заняли примерно в 1.83 раза больше времени, чем один. Вывод относится к одинаковому числу обучающих примеров.

Эта серия поддерживает пользу дополнительной глубины в данной конфигурации. При небольшой экономии общего числа параметров связывание весов уступило независимым блокам. Сравнение этой серии с GPT из RL-экспериментов включает изменение архитектуры и длины истории.

## 8. Дополнительные ветви

**Смешивание GPT с частотным распределением истории.** При замороженном GPT обучался небольшой gate, выбирающий вес двух распределений. Gate поверх полного GPT дал NDCG .1345; поверх продолженного CE — .1373. Последний включал дополнительный fit на 4,11 млн примеров. Это практический составной вариант, отдельно от сравнения CE/RL.

**Построение списка на малом пуле.** Для 16 кандидатов и списка из четырёх треков сравнивались myopic-политика, точные continuation values и обучаемые SubTB-варианты при фиксированной реальной истории. Награда включала RM и штраф за избыточную похожесть. Покрытие реальных рекомендованных целей было около 2.2%; разница точного Q с myopic по заданной utility — около .0006. Такой пилот ограничен поддержкой кандидатов и малым запасом улучшения utility.

**Размер обучающего пула и readout-модули.** Проверялись дообучение на полном и ограниченном наборе позиций от одной исходной модели, обучение с нуля на разных пулах и повторные readout по замороженным представлениям. Их статусы и результаты перечислены в приложении ниже.

## Обсуждение

Next-item loss и доля прослушивания задают разные цели: какой трек окажется следующим и насколько полно будет прослушан уже выбранный трек. RM обучена на зарегистрированных взаимодействиях. Прогноз для произвольного кандидата переносит эту зависимость за пределы наблюдавшегося выбора. Поэтому её полезность для рекомендаций проверялась отдельно: через точный RM-оптимум, замену истории, релевантность и распределение действий.

Эти проверки локализуют результат основной серии: RLOO обучается оптимизировать заданную RM; преимущество по следующему зарегистрированному треку получает CE. Архитектурная серия проверяет другую гипотезу — пользу дополнительных вычислений над историей — и до этапа RL не доводилась.

Свободная генерация пяти треков с добавлением каждого в историю и оптимизация возврата пользователя здесь не выполнялись. Для следующего исследования можно обучить прогноз возврата в течение 24 часов и сравнить `r(h,i)` с history-only `r(h)`. Метка должна целиком созревать внутри своей части разбиения: `t+24h ≤ cutoff`. Затем влияние рекомендательной политики на возврат проверяется онлайн.

Время обучения одного варианта с контекстом 256 составило около 32 минут для одного прохода и 59–61 минуты для четырёх.

## Воспроизведение

Пакет содержит код, конфигурации, логи и массивы рангов опубликованных моделей. Исходный parquet скачивается отдельно; крупные веса в Git не включены. Ниже — подготовка данных, обучение основной серии с нуля и оценка новых checkpoints. Новые обучения дают собственные веса и контрольные суммы; для проверки опубликованных чисел сохранены массивы рангов.

Следующий фрагмент создаёт manifest, соответствующий новым весам, и локальную копию RL-конфига с их реальными SHA. `run_rl_grouped.py` проверяет feature manifest, aux manifest и SHA каждого checkpoint; manifest здесь является JSON с перечнем весов, его SHA записывается в конфиг.

```bash
$PY - <<'PY'
import hashlib, json
from pathlib import Path
root=Path('runs/aux')
sha=lambda p: hashlib.sha256(p.read_bytes()).hexdigest()
names=('checkpoint_gpt_seed43_fullsupported.pt','checkpoint_combined_seed17_primary.pt','checkpoint_history_seed17.pt')
files={n:sha(root/n) for n in names}
(root/'manifest.json').write_text(json.dumps({'schema':'local-retraining-v1','files':files},sort_keys=True,indent=2)+'\n')
cfg=json.loads(Path('configs/rl-full43-ce-rloo8-20261025.json').read_text())
cfg.update(
    base_checkpoint_filename=names[0],
    base_checkpoint_sha256=files[names[0]],
    combined_rm_checkpoint_sha256=files[names[1]],
    history_rm_checkpoint_sha256=files[names[2]],
    feature_manifest_sha256=sha(Path('data/processed/yambda100k-eventuniform/manifest.json')),
    aux_manifest_sha256=sha(root/'manifest.json'),
    base_training_manifest_sha256=sha(Path('data/processed/yambda100k-fullsupported-eventuniform/manifest.json')),
)
Path('runs/rl-config-local.json').write_text(json.dumps(cfg,indent=2)+'\n')
PY
CUDA_VISIBLE_DEVICES=0 $PY scripts/run_rl_grouped.py --data data/processed/yambda100k-eventuniform --aux runs/aux --config runs/rl-config-local.json --output runs/rl --seed 17 --device cuda &
pid17=$!
CUDA_VISIBLE_DEVICES=1 $PY scripts/run_rl_grouped.py --data data/processed/yambda100k-eventuniform --aux runs/aux --config runs/rl-config-local.json --output runs/rl --seed 29 --device cuda &
pid29=$!
wait "$pid17"
wait "$pid29"
```

В примере два seed запускаются параллельно на двух GPU; каждому процессу видна одна. На одной GPU выполните обе команды последовательно с `CUDA_VISIBLE_DEVICES=0`. Скрипты сохраняют ход validation, веса и метаданные в указанные каталоги. Финальные CE/RLOO checkpoints находятся в `runs/rl/seed-{17,29}/{ce,rloo8}/step-32000.pt`.

### Оценка новых моделей

Для базового GPT и новых CE/RLOO checkpoints применяется одна функция оценки по всему тестовому каталогу:

```bash
PYTHONPATH="$PWD/src:$PWD/scripts" $PY - <<'PY'
import json
from pathlib import Path
import numpy as np
import torch
from recsys_tt2.batching import open_event_arrays
from run_rl import load_policy
from run_experiments import eval_policy

data = Path('data/processed/yambda100k-eventuniform')
arrays = open_event_arrays(data)
indices = np.load(data/'test_indices.npy', mmap_mode='r')
device = torch.device('cuda' if torch.cuda.is_available() else 'cpu')
paths = [Path('runs/aux/checkpoint_gpt_seed43_fullsupported.pt')]
paths += [Path(f'runs/rl/seed-{seed}/{arm}/step-32000.pt')
          for seed in (17, 29) for arm in ('ce', 'rloo8')]
for path in paths:
    model, _, _ = load_policy(path, device)
    metrics = eval_policy(model, indices, arrays, batch_size=128, device=device)
    result = {group: metrics[group] for group in ('all', 'organic', 'recommended')}
    print(json.dumps({'checkpoint': str(path), 'test': result}, ensure_ascii=False))
    del model
PY
```
